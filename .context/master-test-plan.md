## 2. Executive risk map

Welcome to Bunkai QA. Before you touch a browser or a spec file, you need the lay of the land, because Bunkai is a system where the **data model is the product**. The structural rule — every ATC must anchor to a User Story *and* at least one Acceptance Criterion — isn't a nice-to-have; it's the pedagogy and the traceability promise, enforced at the constraint layer, not in a README. That means the two things you'll lose the most sleep over are **what writes the data** (the ATC transaction, the Run step-mark recompute) and **what lets people in** (auth, PATs, RLS). Everything else — dashboards, tree view, coverage, traceability — is downstream of those two, and will happily show you garbage if the writes upstream are wrong.

There's also a whole class of **derived and background state** that fails without telling anyone: `run_atcs.status` and `runs.progress_pct` are recomputed transactionally on every step mark, `module_defect_stats` is a materialized view refreshed by trigger plus a nightly fallback, and three crons (`run-timeout-sweeper`, `idempotency-cleanup`, `jira-bug-sync-retry`) are the only thing standing between the system and phantom runs, unbounded tables, and silently-unsynced bugs. Two of those crons don't exist in the target repo yet — treat every silent-killer claim below with that asterisk.

One known finding shapes how you test the runner: the step-result endpoint is **`POST /api/v1/runs/{id}/steps/{stepId}/mark`**, not `/result` as the SRS and data-map diagrams say. Docs are stale; the code is truth. Target `/mark`.

## 3. What to test first and why

### CRITICAL — Run step-mark & lifecycle (Flows 2 and 3)

**Why it matters.** This is the heartbeat of the product. Every `POST .../steps/{stepId}/mark` updates a leaf row, recomputes the parent `run_atcs.status`, recomputes `runs.progress_pct`, and broadcasts over Realtime — all in one transaction. Manual runs, agent runs, and (Phase 2) CI imports all hit the exact same endpoint and produce the exact same data shape. If this rollup is wrong, **every dashboard in the system is wrong**: run history, status dots in the tree, defect heatmap, coverage, traceability. Users don't notice a subtly-wrong progress bar — they notice that a red "failed" run shows green on Mateo's dashboard, and trust is gone.

**What commonly breaks.**
- Rollup precedence: `any fail → fail` is sticky; `block` only when blocked and nothing failed; `pass` only when *all* steps pass; anything else `running`. Edge: a step marked `block` after a prior `fail`, or a `fail` after a `block` — precedence must hold.
- Step marks against a terminal Run. The state machine is absorbing: once `passed|failed|aborted`, `mark` must reject. Agents with stale state (or a replayed idempotency key from before finish) will try exactly this.
- The skeleton on Run start: `POST /runs` must materialize every `run_atcs` and every `run_steps` row in one shot, all `pending`, ordered by the chain. A missed row shows up as "step missing" mid-run.
- `progress_pct` math: completed over total. What counts as completed — marked steps only, or the skipped sweep on abort/finish?
- The **`/mark` vs `/result` trap**: docs say `/result`, code says `/mark`. Your automation must use `/mark` or it 404s and you'll spend an hour wondering why.

**Dependencies.** Test chains (the skeleton comes from `test_steps`), environments (a Run targets one), ATCs (snapshot semantics — `run_steps` must hold the executed content, not a live ref), and the whole reporting stack downstream.

**What an experienced QA would check.**
- Full lifecycle: start → mark every step pass → finish `passed`, verifying `run_atcs` and `progress_pct` at each mark and that the response `derived` block matches what you'd compute by hand.
- Mixed-verdict runs: one fail among many passes, a block, then confirm the run rolls `failed` at finish even if the last marked step was a pass.
- Terminal guards: mark, abort, and finish after the Run is terminal — all rejected, and remaining steps swept to `skipped` on abort/finish.
- Idempotency: same `Idempotency-Key` on `POST /runs` within 24h returns the same `run_id`; a *different* key creates a second Run. Then the nasty one — replay the start key *after* the first Run finished and confirm the agent can't write into a terminal Run through the replay path.
- Agent path parity: drive the same test with `executor.type=agent` and confirm dashboards/run history show identical shape, and that a bare Bearer token (no cookie) with `run:execute` scope can do the whole loop.

### CRITICAL — ATC authoring & edit propagation (Flow 1, the heart)

**Why it matters.** ATCs are the atomic product unit. Creation is a **4-table transaction** (`atcs` + `atc_steps` + `atc_assertions` + `atc_acceptance_criteria`) with two hard structural rules: the ATC must name a User Story, and at least one of its ACs must belong to that Story. Edit is worse: increment `version`, replace steps/assertions in a cascade, and **silently change every Test that chains it** — that's the "one-edit-many-tests" promise. The whole marketing thesis of the product is that orphan tests cannot exist and that maintenance collapses to a single edit. Break that and you've broken the reason anyone buys Bunkai.

**What commonly breaks.**
- The transaction is all-or-nothing: a bad step position, a missing layer, or an AC belonging to a *different* Story must roll back everything, not leave a half-ATC.
- Edit propagation: a 6-step ATC edited to 4 steps must shrink every chained Test, and a version bump must surface somewhere (usage report, activity) so nobody runs a stale script believing it's current.
- AC re-binding on edit: reassigning the ATC to another AC or a different module must re-validate against the Story, exactly like create.
- Slug computation (`{module-slug}/{atc-id-padded}`) and the namespace hierarchy — rename the module and watch the paths.

**Dependencies.** US + AC CRUD above it; `test_steps` below it; every Run that snapshots it.

**What an experienced QA would check.**
- Create with valid bindings → full ATC with ordered steps/assertions; then each validation: no US, no AC, AC from another Story, wrong layer, zero steps, non-sequential positions → each rejected atomically.
- The propagation blast radius: build Test A and Test B both chaining ATC-X, edit X, verify both Tests reflect the change immediately (GET expanded view), and that `GET /atcs/{id}/usage` reports both with correct positions.
- Version drift: confirm `version` increments on each edit and that activity log records the edit with affected test count.
- Cross-project poisoning: an ATC whose module belongs to Project P must never be chainable into a Test of Project Q (the `PUT /tests` same-project validation is your guard).

### CRITICAL — Auth & identity: all four tiers

**Why it matters.** Security gate with four tiers — browser session (cookie JWT), headless PAT from signin/confirm (no `workspace:admin`), session-scoped PAT from `/tokens` (any scope with role gate), and public read-only. A single `resolveIdentity` collapses cookie and Bearer into one Principal, and RLS does the rest. Two leaks to fear: a stolen PAT (a live one is a standing workspace takeover — it's a hash in `access_tokens` with scopes attached), and a bypass that lets a viewer or a `workspace:admin`-less bearer do writes. Both are silent until someone notices data they shouldn't see.

**What commonly breaks.**
- PAT lifecycle: mint → use → revoke → use again. Revocation is `revoked_at`; the middleware must see it on the next request (no cache of token validity beyond the request).
- Scope enforcement: a read-only PAT (`atc:read`) calling `POST /atcs` → 403; a headless-minted PAT requesting `workspace:admin` → rejected at mint (it cannot be minted headless at all).
- Session expiry / refresh in the browser via middleware — expired JWT should redirect, not 500.
- Anti-enumeration and rate limiting: signup 409 uniform, signin 401 uniform, magic-link same-200, OTP resend — plus the known `check-email` leak (`{exists, confirmed}` with no app-level rate limiter, accepted in ADR-0007 but begging for a brute-force test).
- Token secret shown once at issuance — re-fetching `/tokens` must never return the secret.

**Dependencies.** Everything. Every flow below here assumes the Principal is right.

**What an experienced QA would check.**
- The four-tier matrix against a representative write (create ATC) and a representative execute (start run): cookie session ✓, headless PAT ✓ if scoped, read-only PAT ✗, public ✗.
- Revoke-and-reuse: mint a PAT, use it, revoke it, immediately retry → 401 uniform (no info leak in the error body).
- Role ladder: viewer read, member write, admin manage-members, owner workspace-delete — each attempted one step above its ceiling.
- Auth-path parity in the browser: signup → OTP confirm → auto workspace bootstrap; magic-link cross-device (BK-400); OAuth callback with a tampered `bk_oauth_state` cookie.

### CRITICAL — Multi-tenancy RLS isolation

**Why it matters.** Hard multi-tenancy at the DB layer. Every business table carries `workspace_id` (directly or via parent) and RLS policies gate reads/writes by active membership. This is security-by-architecture: a single misconfigured policy, a missing `workspace_id` on a table, or a service-role query that forgot its explicit filter leaks one customer's test data to another — with **no UI feedback at all**. It's the quietest way to lose the company. The mitigation note in the architecture (indexed `workspace_id` + `SET LOCAL row_security = off` for trusted service-role jobs) is exactly the kind of escape hatch that grows a policy gap if someone adds a new table and forgets both halves.

**What commonly breaks.**
- A new table or RPC added without a policy → either locked (all users 403) or wide open (cross-tenant read).
- Service-role (admin client) paths that pre-filter explicitly — one forgotten filter and the isolation is gone.
- The invite path crossing workspace boundaries, and `role ≤ inviter's role` on invites.
- Subtree scoping: "list ATCs in module X" must respect the module's *project* → *workspace* chain, not just the direct id.

**Dependencies.** Every entity, every RPC, every dashboard query.

**What an experienced QA would check.**
- Tenant A vs tenant B: create mirrored data in two workspaces; verify A's reads (API and RLS-direct) never return B's rows, and vice-versa, for Projects, Modules, ATCs, Runs, Bugs, tokens.
- Escalation attempts: user B references A's ids directly in POST bodies, filters, and deep links → 404/403, never 200 with data.
- Viewer write attempts and PAT scope bypasses across workspaces.
- A regression sweep after any schema change: the existing isolation tests on traceability (`traceability-*-isolation.test.ts`) are your canary — keep them green.

### HIGH — Bug filing, lifecycle & Jira sync (Manual Run, steps 4-5)

**Why it matters.** Bugs are the native defect record: `module_id` mandatory (the heatmap axis), auto-linked `atc_id`/`run_id` when filed from inside a failing Run, `steps_to_reproduce` pre-filled from the executed steps. The bug lifecycle (`open → in_progress → resolved → closed`, with reopen allowed for regressions) feeds recovery-cycle and reopen-rate metrics. If filing is painful or the pre-fill is wrong, QAs stop filing from the runner — and the heatmap dies. Jira sync is **best-effort by design** (bug stays usable natively), but silent sync failure means developers never see the ticket and QA thinks they did.

**What commonly breaks.**
- The pre-fill drawer: wrong module inherited, missing ATC/run link, steps_to_reproduce from the wrong steps.
- Severity P1-P4 acceptance and the keyboard shortcuts.
- `module_defect_stats` refresh on bug create — the heatmap must update within the success criterion (about 5s).
- Status transitions with the required reason on "won't fix"-style closes, and activity-log rows per transition.
- Jira sync: `jira_sync_status` stuck `failed`, retry loop, or external_id written to the wrong issue.

**Dependencies.** Runs (for the pre-fill), Modules, Jira integration config, materialized view.

**What an experienced QA would check.**
- File from a failing step → module/ATC/run auto-filled and `steps_to_reproduce` mirrors the executed steps; file standalone from the Bugs view → optional links, still requires module.
- Full lifecycle to `closed`, then a regression reopen, verifying reopen is counted and visible in metrics.
- Sync failure paths: Jira unreachable at create time → bug saved, `jira_sync_status=failed`, retry later flips it; confirm the external_id/URL round-trip.
- Heatmap freshness: create a bug, poll the heatmap endpoint, confirm the module count ticks up.

### HIGH — Jira import (one-way pull, Setup step 5)

**Why it matters.** This is how QA teams on Jira bootstrap Bunkai without retyping their backlog. An async worker pulls Jira REST `search` in pages, converts ADF→Markdown, heuristically extracts AC bullets, dedupes by `external_id`, and places stories in a matching module or `Inbox`. It's a productivity feature — but a silent partial failure (some issues imported, others quietly dropped) is worse than a loud total failure, because you think your backlog is in Bunkai when it isn't.

**What commonly breaks.**
- The AC extraction heuristic: "Acceptance criteria" / "AC:" / numbered-list-under-heading — a Jira description that uses none of these produces US with zero ACs, which then can't be marked `ready_to_test`.
- The 500-issue cap: a job over the cap must chunk or tell the user, not truncate.
- Idempotent re-import: re-running the same JQL must update, not duplicate.
- Worker death mid-import: `import_jobs` stuck in `running` forever (there's no timeout sweeper for imports — see section 5).
- Module matching: component → module name matching, and the `Inbox` fallback.

**Dependencies.** Jira REST, `integrations` config + `ATLASSIAN_*` secrets, `import_jobs`, modules.

**What an experienced QA would check.**
- Happy path with a sandbox Jira: JQL → US + AC rows, dedupe on re-run, module placement.
- Extraction stress: descriptions with all three AC styles, mixed, and none — confirm AC count per US and that the UI flags zero-AC stories.
- Failure paths: bad JQL → job `failed` with error surfaced in `/imports/{id}`; auth failure → `JiraAuthError` → job `failed`; then verify a retry after fixing config actually succeeds.

### HIGH — Test chain authoring & reorder (FEAT-023/024)

**Why it matters.** A Test is an ordered chain of ATC references — not copies. Getting the chain wrong poisons every Run that comes after: wrong order, cross-project ATC, duplicate positions, or a reorder that silently drops an ATC. Since Runs snapshot the chain at start time, a chain bug is baked into run history permanently.

**What commonly breaks.**
- Reorder diff logic: `PUT /tests/{id}` diffs old vs new chain — insert, remove, move, and the "same ATC at multiple positions" case (allowed, and easy to mangle).
- Same-project validation: an ATC from another project must be rejected.
- Empty-chain guard and duplicate-position guard.
- Tags: reserved vocabulary (`smoke|sanity|regression`) recognized for filter semantics, custom tags coexisting.

**Dependencies.** ATCs, `test_steps`, Runs (skeleton source).

**What an experienced QA would check.**
- Build a chain, run it (skeleton order matches), then reorder and confirm the next Run follows the new order while the previous Run's snapshot is unchanged.
- Move/duplicate/shrink a chain and verify position rebalancing is 1..n with no gaps.
- Cross-project ATC attempt → rejected; reserved-tag filter → correct subset.

### HIGH — Coverage, heatmap & traceability views

**Why it matters.** These are the "so what" screens for QA leads. Coverage distinguishes **authoring gaps** (AC with no ATC) from **execution gaps** (ATC never run). The heatmap rolls defect count and week-over-week trend per module. Traceability walks AC → ATC → Test → Run → Defect with gap states (`Uncovered`, `No test written`, `No run recorded`). These screens *inherit* correctness from the write path — if runs or bugs are wrong upstream, these lie. Test them, but remember they're symptoms, not causes.

**What commonly breaks.**
- Materialized-view staleness (`module_defect_stats`) rendering yesterday's numbers with no freshness indicator.
- Gap-state classification: an ATC that exists but was only run in a `running`/aborted Run — is it "no run recorded" or "uncovered"?
- Trend math across the rolling window (7d/30d/90d) and week-over-week percent at window edges.
- Recovery cycle (median time first-fail → first-pass) when a Run was never failed or never passed.

**Dependencies.** Runs, bugs, materialized view, tree.

**What an experienced QA would check.**
- Set up a known state: one covered-and-run AC, one covered-not-run ATC, one uncovered AC → confirm the three views classify them distinctly.
- Create/close bugs and confirm heatmap buckets shift within the success window; force a refresh failure and see what the UI does (it likely shows stale — that's a gap to report).
- Traceability chain integrity after an ATC edit and after a module archive.

### MEDIUM / LOW short-list

- **MEDIUM — ATC search & autocomplete (FEAT-019):** `tsvector` GIN index; needs data-volume testing and a check that edits reindex promptly (see section 5). Rank + recency behavior at 2k+ ATCs.
- **MEDIUM — Tree view + status dots (FEAT-038/041):** recursive CTE, depth ≤6 with soft warning at 4, status-dot aggregation per subtree, Realtime partial refetch. Navigation is the daily interface — a broken tree is a bad day, though not a data-integrity day.
- **MEDIUM — Dashboards (home KPIs, activity stream):** read-only aggregates; sanity-check the 4 stat cards against known data and the activity timeline against a scripted session.
- **MEDIUM — Environments (FEAT-012):** deletion blocked while Runs reference it; unique-per-project naming; seeded Staging/Production.
- **MEDIUM — Notifications (FEAT-048/049):** per-user inbox, RLS-visibility of entities, preference categories (run lifecycle / bug lifecycle / mention).
- **MEDIUM — Command palette (FEAT-040):** multi-source search + weighted ranking; test at scale and across workspace boundaries.
- **MEDIUM — Milestones (FEAT-047):** date chips ("Due today" / "N days left" / "N days past target"); Test Plan aggregation **not built** (BK-206).
- **LOW — View-state persistence, workspace switching, bulk-edit:** convenience; cover lightly or defer.

## 4. State machines that matter

Only the machines with operational or legal weight are here. Cosmetic states (module archive, environment lifecycle) are covered by their flows above.

### `runs.status` — the absorbing-terminal machine

```
running ──► passed | failed | aborted   (all terminal, no exit)
```

Why it matters: terminal is **irreversible**. Every dashboard, status dot, and run-history filter derives from these three terminal states. The business consequence of an illegal transition is corrupt history — a run that was `failed` becoming `passed` silently rewrites yesterday's quality verdict. Guard points: no transition out of terminal, step marks rejected on terminal runs, and the sweeper forcing `running → aborted` after `max_duration` (4h default).

Most likely to break: the **finish-with-pending** path — `POST /finish` must sweep remaining steps to `skipped` or reject; and the **reopen temptation** — a QA wanting to continue a finished run must start a new Run, not mutate the old one. Corruption detection: today this is **manual** (someone notices a passed run they remember failing). There is no alert on illegal writes — worth a log assertion in QA strategy.

### `run_atcs.status` — the derived machine (never client-written)

```
pending ──► running ──► pass | fail | block | skipped
```

Why it matters: it's the aggregation layer between step results and the Run verdict, recomputed inside every step-mark transaction. The **precedence rule** is the whole game: any `fail` → `fail` (sticky — later passes don't undo); else any `block` → `block`; all `pass` → `pass`; else `running`; and `skipped` only via parent-abort cascade. The business consequence of a wrong derivation is a green dot on a failed feature — the single most corrosive bug this product can ship. It's invisible: the client never writes it, so nobody double-checks it. Detection: none automatic — you must cross-check the derived value against the step set in tests.

### `bugs.status` — the defect lifecycle with a deliberate reopen

```
open ──► in_progress ──► resolved ──► closed
  ▲                                      │ reopen (regression on same defect)
  └──────────────────────────────────────┘
```

Why it matters: reopen is a **deliberate state regression**, allowed and counted (reopen rate feeds metrics; recovery cycle reads first-fail→first-pass). A broken transition — a `closed` bug that can't reopen, or a "won't fix" close without a reason — silently corrupts the defect-metrics story. Guard the four canonical transitions and the explicit-reason close. Detection: activity-log rows per transition; verify each transition writes one.

### `imports.status` — the job machine with no timeout guard

```
pending ──► running ──► succeeded | failed
```

Why it matters: an import stuck `running` is invisible — the user polls `/imports/{id}` and it never resolves. There is **no timeout sweeper for imports** (unlike runs). A worker that dies mid-pull leaves the job orphaned forever and the UI showing "importing…". This one you test defensively: force a worker failure and see whether `failed` is ever written, or whether the row rots in `running`.

## 5. Silent killers — automated processes

These are the processes with **no UI feedback path**. Score them separately: even a rare silent failure is CRITICAL because it rots unnoticed. Bold = highest risk.

### 1. **`run_atcs.status` + `runs.progress_pct` recomputation** (DB-trigger-in-transaction)
On every step mark, the same transaction folds child statuses up. If the recompute logic breaks (or the transaction splits), runs silently misreport. Detection today: none — the response `derived` block is the only surface, and the UI trusts it. **QA strategy:** assert `derived` against manually-computed expectations across every precedence combination; treat any recompute change as release-blocking.

### 2. **Run-timeout sweeper** (cron, 15 min, `max_duration` 4h)
Marks abandoned `running` runs as `aborted`. **Not implemented in the target repo yet** (no cron routes). If it's missing or late: an agent-abandoned Run stays `running` forever — phantom "Active Runs" on dashboards, run history polluted, and worst of all **step marks still accepted on a zombie run** because it's not terminal. Detection: none until someone counts active runs. **QA strategy:** once it ships, synthetic probe — start a run with a tiny `max_duration`, wait past it, verify abort; assert `abort_reason="executor timeout"` and remaining steps `skipped`.

### 3. **`idempotency-cleanup`** (cron, hourly, 24h TTL)
Deletes expired keys. Miss a run → table grows unbounded (operational, not corrupt). But delete *early* (clock skew, DST) → a retried POST re-executes and **duplicates state** — e.g., a second Run, a second ATC, a second Bug. Detection: none. **QA strategy:** boundary tests on TTL — key at 23h59m still returns cached response, key past 24h creates new state; watch DST transitions if the expiry is computed in local time.

### 4. **`jira-bug-sync-retry`** (cron, 5 min, exponential backoff)
Retries bugs stuck `jira_sync_status=failed`. **Not implemented in the target repo yet.** Without it, a transient Jira outage leaves bugs permanently unsynced and — because `jira_sync_status` isn't exposed in the `GET /bugs` list (known gap) — QA can't even see which ones. Detection: none in the UI. **QA strategy:** once it ships, deliberately fail a bug create against Jira, confirm `failed`, then recover Jira and confirm the retry converges; check backoff doesn't hammer (1→16s) and respects the 5-min cadence.

### 5. **`module_defect_stats` materialized-view refresh** (trigger on bug INSERT + nightly fallback)
Stale view → heatmap and defect counts show yesterday's truth with zero indication. Detection: none (a "last refreshed" stamp would help — worth requesting). **QA strategy:** after creating a bug, poll the heatmap within the ~5s success criterion; if the nightly fallback exists, kill the trigger path and confirm the nightly still converges.

### 6. **Realtime fan-out** (Supabase logical replication → WebSocket)
Broadcasts `runs`, `run_atcs`, `run_steps`, `bugs` to subscribed tabs. If the channel dies or fan-out is plan-limited, the **UI goes stale silently** — Mateo's dashboard stops moving and nobody knows. Detection: none in-app; WebSocket reconnection is silent. **QA strategy:** reconnect tests (kill the socket mid-run, confirm state resyncs), and multi-tab consistency checks (two tabs marking steps must agree).

### 7. **`tsvector` index maintenance on `atcs`**
Search and autocomplete read the GIN index. A missed index update → searches silently miss brand-new or freshly-edited ATCs. Detection: none. **QA strategy:** create/edit an ATC, immediately search for its title/tags; volume-test ranking with thousands of ATCs; confirm subtree + layer filters combine with ts_rank.

### 8. **Soft-delete cascade on Module archive**
`archived_at` set on descendants — Modules, US, AC, ATC, Tests. **Runs and Bugs are not in the listed cascade scope.** Archive a module that has run history and bugs: do the Runs survive? Do bug heatmap rows now point at an archived module? Nobody sees a warning. **QA strategy:** archive a module with runs + bugs and verify (a) what remains visible, (b) heatmap/traceability handling, (c) whether rerunning an archived test is possible. Report the behavior as a product decision.

### 9. **Jira import worker** (`after()` on Vercel, no import-timeout sweeper)
An import that dies mid-pull leaves `import_jobs` in `running` forever (see `imports.status` above). Detection: only by polling. **QA strategy:** force a worker failure, confirm `failed` is written or file the gap; verify the client poll shows a terminal state and surfaces errors.

## 6. External integrations — failure points

| Service | Which flow stops | Critical timeouts / retries | Acceptable degradation | Known quirks |
|---|---|---|---|---|
| **Supabase Auth** | Everything behind login (signup, confirm, signin, magic-link, OAuth) | Session refresh via middleware; OAuth blocked → fallback magic-link visible within ~30s | Hard-fail: no auth, no app | 429 with `Retry-After`; 401 uniform; `check-email` leaks `{exists, confirmed}` (no rate limiter) |
| **Supabase Postgres + RLS** | Every request, all flows | Pool exhaustion → 500; RLS violation → 403 | Hard-fail | Business logic in `bunkai_*` SECURITY DEFINER RPCs; single project shared across local/staging/prod — data NOT isolated between envs |
| **Supabase Realtime** | Live runner + dashboards (Flow 2/3 refresh) | WebSocket reconnect, silent | Degrades to stale UI (no error) | Fan-out limited by plan; logical replication; tree uses partial per-subtree refetch |
| **Supabase Storage** | Evidence uploads (run steps, bugs) | Signed URL expiry → re-request; quota → 413 | Step still records pass/fail with empty evidence; broken-image placeholder at view time | Client uploads direct via signed URL — Bunkai never proxies blobs |
| **Jira REST API v3** | Import (hard), bug sync (best-effort) | 429 backoff 1→16s, max 5 retries; network → retry | Bug sync: bug stays native, `jira_sync_status=failed`; Import: job `failed` surfaced in poll | Basic auth via `ATLASSIAN_*`; JQL pagination; ADF→Markdown; extraction heuristic is lossy |
| **Cloudflare R2 / MinIO** | Evidence lifecycle (Flow 2 step 4, Flow 3) | Signed URL expiry | Missing evidence, bug still filed | S3-compatible; egress-free (R2); MinIO drop-in for Community |
| **Resend (indirect, via Supabase GoTrue templates)** | OTP + magic-link delivery (onboarding, login) | None at app level — Supabase manages | Delivery failure = user can't complete auth; fallback is re-requesting | App does NOT read `RESEND_API_KEY` — `.env.example` is misleading |
| **Vercel (hosting + `after()`)** | All flows; background jobs (import) | Cold start ~500ms; `after()` timeout → job incomplete | `after()` failure = stuck import_jobs | Cron is Phase 2; import runs on Fluid Compute `after()` |
| **Sentry** | None (observability) | — | Silent drop, no user impact | DSN misconfig → silent |
| **PostHog** | None (analytics) | — | Events lost in queue | Key missing → silent |

The failure-point rule of thumb: **only Jira bug-sync and evidence upload are soft-fail by design.** Everything else is hard-fail or silently-stale, so your integration tests should focus on *degradation honesty* — does the UI tell the truth about what failed, or does it look like success?

## 7. Dependency cascade between flows

```
ATC authoring ──► Test chain ──► Run skeleton ──► Step marks ──► run_atcs / progress
      │                │              │               │                │
      │                │              │               │                ▼
      └── AC anchors   └─ same-proj   └─ env          └─ derived ──► dashboards, coverage,
                      validation      selection          │           traceability, status dots
                                                          │
      Auth / PAT ──► RLS ──► [every write above]          ▼
                                                Bug filing ──► heatmap ──► Jira sync
```

The three chains that actually matter:

1. **ATC → Test → Run → Bug → Heatmap.** An ATC edit ripples into every chained Test, which becomes a Run skeleton, whose step marks drive rollups, which feed the bug that increments the heatmap. A bug here at *any* hop shows up everywhere below it — testing the runner in isolation while an ATC edit silently reordered your steps will leave you chasing a "regression" that's actually a propagation artifact.

2. **Auth / PAT → RLS → every write.** A weak link here isn't one broken flow — it's *every* flow operating under a false identity. If a viewer can write, or a token survives revocation, all the carefully-tested flows above suddenly execute with the wrong permissions, and the isolation tests are the only thing that catches it.

3. **Jira import → US/AC → ATC.** Import is the onboarding tap. If it silently drops ACs (extraction heuristic), every ATC built on those stories is structurally weak — `ready_to_test` gates never trip, coverage shows authoring gaps that aren't really gaps.

The point of the cascade: testing flow A in isolation hides breakage that only surfaces in `A → B → C`. Your regression suite should contain at least one end-to-end journey that walks ATC edit → chain → run → bug → heatmap in a single script, because no unit test catches a propagation slip.

## 8. Edge cases developers commonly forget

Grouped by theme, with the specific Bunkai flow most at risk.

**Concurrency.** Two executors (two agents, or an agent + a human, or two tabs) marking steps on the same Run. Last-write-wins on `run_steps` is fine — but the recompute must not tear under concurrent marks. Also: two editors on the same ATC, both hitting `PUT /atcs/{id}` — version increments must not silently drop one editor's changes. Risk flow: Run step-mark; ATC edit.

**Idempotency.** The 24h replay window is a feature for agents, a footgun for humans. Replaying a `POST /runs` key returns the original `run_id` — then the replayer marks steps on a Run that may already be terminal (rejected, good), or worse, on a *still-running* Run it doesn't own. Confirm key scoping is `(endpoint, key, user, workspace)` so two workspaces can't collide on the same key string. Risk flow: Run start; Bug create (a replayed bug POST duplicates a defect with `jira_sync_status`).

**Data limits.** Step content max 2KB, description max 50KB, evidence max 10 URLs, tags ≤10, module depth ≤6 (soft warn at 4), Jira import cap 500 issues/job. Each limit should fail loudly with a 4xx + code, not truncate silently. The nastiest: the import 500 cap — a truncated import looks successful. Risk flow: ATC create; Jira import.

**Timezone / DST.** The run-timeout sweeper computes `now - started_at > max_duration`; if `started_at` is stored in UTC and compared in local time, a DST shift silently changes the timeout window. Same for run history `date_from/date_to` filters, heatmap week-over-week buckets, and milestone "days left" chips. Risk flow: Run lifecycle; Metrics; Milestones.

**Permission boundaries.** The classic IDOR: passing another workspace's `project_id`/`atc_id`/`run_id` in a POST body or deep link. RLS should 404/403, but every new endpoint is a new chance to route around it. Also: `workspace:admin` is un-mintable headless — a CI token that *should* be able to do admin work will 403 and the error won't say why. Risk flow: RLS isolation; PAT scopes.

**Orphaned states.** What happens to Runs when their Test or Module is archived? Bugs when their Module is archived? Environments when referenced by a Run (deletion is blocked — good — but rename?) ATCs when their US is archived? The soft-delete cascade covers US/AC/ATC/Test under Module, but **Runs and Bugs are not in the cascade scope** — an un-verified orphan path. Risk flow: soft-delete cascade (section 5, item 8).

**Realtime staleness.** Out-of-order or missed broadcasts leave a tab showing a status dot / progress bar that's behind the DB. The UI has no "you may be stale" indicator. Two-tab test: mark a step in tab A, confirm tab B converges. Risk flow: Realtime fan-out; tree status dots.

## 9. Pre-release checklist (priority-ordered)

Each line is one check: "Verify X does Y under Z". CRITICAL first, then HIGH.

1. Verify `POST /runs/{id}/steps/{stepId}/mark` recomputes `run_atcs.status` and `runs.progress_pct` transactionally for every precedence combination (fail sticky over block/pass, block over pass, all-pass → pass).
2. Verify step marks, finish, and abort are rejected on terminal Runs, and that abort/finish sweep remaining steps to `skipped`.
3. Verify `POST /runs` materializes the full run_atcs + run_steps skeleton in the chain order, and that idempotency (same key, 24h) returns the same `run_id`.
4. Verify ATC create is atomic across the 4 tables and rejects an AC that doesn't belong to the ATC's User Story.
5. Verify an ATC edit propagates to every chaining Test (expanded view + usage report) and increments `version`.
6. Verify the four-tier auth matrix against create-ATC and start-run (session ✓, scoped PAT ✓, read-only PAT ✗, public ✗).
7. Verify PAT revocation invalidates on the next request and token secret is never returned after issuance.
8. Verify RLS isolation between two workspaces on Projects, ATCs, Runs, Bugs, tokens — including direct-ID escalation attempts.
9. Verify bug-from-run pre-fill carries module + atc_id + run_id + steps_to_reproduce, and bug create refreshes the module heatmap within ~5s.
10. Verify bug lifecycle open → in_progress → resolved → closed writes an activity-log row per transition, and reopen is allowed and counted.
11. Verify Jira import is idempotent on `external_id`, honors the 500-issue cap without silent truncation, and surfaces `failed` jobs in `/imports/{id}`.
12. Verify bug Jira sync failure sets `jira_sync_status=failed` (bug stays usable natively) and a retry converges once Jira recovers.
13. Verify a Run executed via Bearer PAT produces identical dashboard/run-history data to a human run.
14. Verify Test chain reorder rebalances positions 1..n, rejects cross-project ATCs, and the previous Run's snapshot is unchanged.
15. Verify module archive cascades `archived_at` to US/AC/ATC/Test and that behavior with existing Runs/Bugs is explicit (documented or corrected).
