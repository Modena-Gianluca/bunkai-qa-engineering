## 1. Executive Summary

Bunkai's API is the **single write surface** for the entire system. There is no "UI-only" path — every action Elena performs in the browser (create ATC, start Run, file Bug) passes through the same Next.js Route Handlers that a CLI, an AI agent, or a CI pipeline calls via Bearer token. This is the structural decision that makes three-mode execution (manual, agentic, automated) possible without conditional logic in dashboards.

The API lives under `/api/v1/` on a Next.js 15 App Router deployed to Vercel. Authentication is unified through a single gateway (`withApiHandler` + `resolveIdentity`) that collapses browser cookie sessions and Bearer PATs into one `Principal` object. Postgres Row Level Security (RLS) is the source of authorization truth — route handlers never re-implement access checks. Business logic lives in PostgreSQL SECURITY DEFINER RPCs (`bunkai_*` functions), keeping the TypeScript layer focused on parsing, validation, and error mapping.

External integrations are limited to four touch points: Supabase (Auth, Postgres, Realtime, Storage) for the core platform, Jira REST API for one-way issue import and optional bug sync, Cloudflare R2 for run evidence blobs, and Resend for transactional email delivery (invoked indirectly through Supabase Auth templates). The API boundary is intentionally thin — the data model enforces structural traceability (ATC ↔ US ↔ AC), not the API layer.

## 2. Permission & Auth Model

### 2.1 Auth Tiers

| Tier | Auth Method | How Obtained | Capabilities | Token Format |
|---|---|---|---|---|
| **Browser session** | Supabase Auth JWT in HttpOnly cookie | OAuth (GitHub/Google), magic-link (PKCE), or email+password signup/confirm | ALL (`atc:read`, `atc:write`, `run:execute`, `workspace:admin`) | JWT (Supabase session) |
| **Headless PAT** (default) | Bearer token via `POST /api/v1/auth/signin` or `/auth/confirm` | Email+password → session + PAT minted in same call | `atc:read`, `atc:write`, `run:execute` (NO `workspace:admin`) | `bk_pat_<prefix12>.<secret>` |
| **Session-scoped PAT** | Bearer token via `POST /api/v1/tokens` (browser session required) | Any scope; `workspace:admin` requires caller is admin/owner of target workspace | Caller-specified subset of 4 scopes | `bk_pat_<prefix12>.<secret>` |
| **Public** | None | Explicit `auth: 'public'` on handler | Read-only introspection | N/A |

### 2.2 Capability Scopes

| Scope | Grants | Routes Requiring It |
|---|---|---|
| `atc:read` | Read ATCs, Tests, Runs, Bugs, Modules, Projects | GET endpoints (implicitly via RLS) |
| `atc:write` | Create/update ATCs, Tests, Bugs, Modules, Projects, US, AC | POST/PUT on `/atcs`, `/tests`, `/bugs`, `/modules`, `/projects`, `/user-stories`, `/acceptance-criteria` |
| `run:execute` | Start, mark steps, abort, finish Runs | POST on `/runs`, `/runs/{id}/steps/{sid}/mark`, `/runs/{id}/abort`, `/runs/{id}/finish` |
| `workspace:admin` | Manage members, invites, integrations, tokens | POST on `/tokens`, `/invites`, `/workspaces/{id}/membership` |

### 2.3 RBAC Role Hierarchy

```
viewer ──⊂ member ──⊂ admin ──⊂ owner
```

| Role | Read | Write Entities | Manage Members | Manage Workspace |
|---|---|---|---|---|
| `viewer` | ✓ | ✗ | ✗ | ✗ |
| `member` | ✓ | ✓ (Projects, Modules, US, AC, ATCs, Tests, Runs, Bugs) | ✗ | ✗ |
| `admin` | ✓ | ✓ | ✓ | ✗ |
| `owner` | ✓ | ✓ | ✓ | ✓ (delete, billing) |

### 2.4 ASCII Token Flow Diagram

```
                    ┌─────────────────────────────────────────────────┐
                    │              BROWSER PATH                       │
                    │                                                 │
  User ──OAuth/OTP──► Supabase Auth ──JWT──► HttpOnly Cookie          │
                    │                              │                  │
                    │         ┌────────────────────┘                  │
                    │         ▼                                       │
                    │  middleware.ts (page routes only)                │
                    │   - createServerClient(@supabase/ssr)           │
                    │   - getUser() refreshes session                 │
                    │   - isProtected(path) → redirect /login         │
                    │                                                 │
                    │         ┌────────────────────┐                  │
                    │         ▼                                       │
                    │  /api/v1/* handlers                             │
                    │   - withApiHandler() wraps every route          │
                    │   - resolveIdentity(request)                    │
                    │     ├─ authHeader starts with "Bearer "?        │
                    │     │   YES → requireBearerToken() → Principal  │
                    │     │   NO  → createClient() → getUser()        │
                    │     │          → Principal (cookie)              │
                    │     └─ principal.db = RLS-scoped client         │
                    │   - handler runs with principal + db            │
                    │   - Postgres RLS enforces workspace isolation   │
                    └─────────────────────────────────────────────────┘

                    ┌─────────────────────────────────────────────────┐
                    │              HEADLESS PATH (CLI / Agent / CI)   │
                    │                                                 │
  Agent ──email+pass──► POST /auth/signin ──► 200 {session, pat}     │
                    │    (or /auth/confirm for new signup)             │
                    │                              │                  │
                    │         ┌────────────────────┘                  │
                    │         ▼                                       │
                    │  Agent stores bk_pat_... token                  │
                    │                              │                  │
                    │         ┌────────────────────┘                  │
                    │         ▼                                       │
                    │  GET /api/v1/me                                 │
                    │   Authorization: Bearer bk_pat_<prefix>.<secret>│
                    │                              │                  │
                    │         ┌────────────────────┘                  │
                    │         ▼                                       │
                    │  requireBearerToken()                           │
                    │   1. Parse prefix (12 chars) from token         │
                    │   2. O(1) lookup: access_tokens.token_prefix    │
                    │   3. Fetch hash from access_token_secrets       │
                    │   4. SHA-256(full_secret) === stored_hash?      │
                    │   5. Check expires_at + revoked_at              │
                    │   6. Return BearerContext {userId, workspaceId, │
                    │      scopes, tokenId}                           │
                    │                              │                  │
                    │         ┌────────────────────┘                  │
                    │         ▼                                       │
                    │  resolveIdentity() → Principal                  │
                    │   db = impersonatingClient(userId)              │
                    │   (anon client + minted user JWT → RLS applies) │
                    └─────────────────────────────────────────────────┘
```

**Key invariant**: A PAT bearer and a cookie session arrive at the handler as the **same `Principal` shape**. The handler never branches on auth method. RLS evaluates identically because both paths produce an `auth.uid()` that Postgres can resolve.

### 4.2 Component Table

| Component | Location | Responsibility | Key Detail |
|---|---|---|---|
| **withApiHandler** | `lib/api/handler.ts` | Wraps every route: request-id, structured logging, error mapping, auth resolution | Default `auth: 'required'` — secure by default |
| **resolveIdentity** | `lib/api/principal.ts` | Unifies cookie + Bearer into single `Principal` | Bearer checked first so PAT never shadowed by stale cookie |
| **requireBearerToken** | `lib/api/middleware/bearer.ts` | SHA-256 hash verify, prefix-indexed O(1) lookup, expiry/revocation check | All failures → uniform 401 (no info leak) |
| **mintPat** | `lib/api/pat.ts` | Generate `bk_pat_*` token, hash + store in sibling table | Secret shown once; 256-bit entropy |
| **createAdminClient** | `lib/supabase/admin.ts` | Service-role client (bypasses RLS) | Used ONLY for token ops, admin lookups, RPCs that take `actorUserId` |
| **createClient** | `lib/supabase/server.ts` | SSR client with cookie session | Used for authed page/API reads where RLS applies naturally |
| **rpc.ts** | `lib/supabase/rpc.ts` | Typed wrappers for all `bunkai_*` SECURITY DEFINER RPCs | Business logic lives in Postgres, not TypeScript |
| **idempotency.ts** | `lib/api/idempotency.ts` | `(endpoint, key, userId, workspaceId) → cached response, 24h TTL` | Prevents duplicate state creation on retry |
| **error-envelope.ts** | `lib/api/error-envelope.ts` | `ApiError` → `{success, error: {code, message, details?}}` | ZodError → 422, unknown → 500 with request_id |

## 5. External Integrations

| Service | Direction | Trigger | Failure Mode | Journeys Affected |
|---|---|---|---|---|
| **Supabase Auth** (GoTrue) | Outbound | signup, confirm, signin, magic-link, OAuth callback | 429 rate limit → retry-after; 401 invalid credentials → uniform error; session expiry → refresh via middleware | 1, 6 |
| **Supabase Postgres** | Bidirectional | Every authenticated request (RLS-scoped reads/writes) | Connection pool exhaustion → 500; RLS policy violation → 42501 mapped to 403; RPC error → mapped per domain | All |
| **Supabase Realtime** | Outbound | Row-change broadcasts on `runs`, `run_atcs`, `run_steps`, `bugs` | WebSocket disconnect → client reconnection; fan-out limited by Supabase plan | 2, 3 (UI refresh) |
| **Supabase Storage** | Outbound | File uploads (evidence, avatars) | Quota exceeded → 413; signed URL expiry → re-request | 2, 3 (evidence) |
| **Jira REST API v3** | Outbound | POST /imports (async background worker) | 401/403 → `JiraAuthError` → import status `failed`; 429 → exponential backoff (1→16s, max 5 retries); network error → retry | 4 |
| **Cloudflare R2** | Outbound | Signed URLs for run evidence (screenshots, video) | R2 down → evidence_url missing (non-blocking, bug still filed) | 2, 3 |
| **Resend** | Indirect | Supabase Auth email templates (OTP, magic link) | Email delivery failure → user cannot complete auth; fallback: retry magic-link | 1, 6 |
| **Vercel** | Host | Deployment, `after()` for background jobs, cron (future) | Cold start → 500ms latency; `after()` timeout → background job incomplete | All |
| **Sentry** | Outbound | Unhandled errors (automatic) | DSN misconfigured → silent (no user impact) | All (observability) |
| **PostHog** | Outbound | Event tracking (automatic) | API key missing → silent (no user impact) | All (analytics) |

## 7. Discovery Gaps

> **Gaps found during API surface analysis — items that diverge from SRS specs or require follow-up.**

| ID | Gap | Impact | Source |
|---|---|---|---|
| **G1** | **Step mark endpoint is `/runs/{id}/steps/{sid}/mark`, not `/result`** as the SRS and data-map describe (`/runs/{id}/steps/{sid}/result`). The functional spec (BK-020) and business-data-map both reference `POST .../steps/{run_step_id}/result`. The live code uses `mark/`. | SRS contracts and data-map flow diagrams reference a non-existent path. Test automation must target `/mark`. | `app/api/v1/runs/[id]/steps/[stepId]/mark/` |
| **G2** | **`import_jobs` table exists** (migration 0020) but was previously flagged as a discovery gap in the data-map (§6, G1). The data-map's §4.6 `imports.status` state machine is now confirmed. | Gap resolved — table exists and is used. | `app/api/v1/imports/route.ts:63` |
| **G3** | **No `/api/v1/runs/{id}/steps/{sid}/result` route exists** — the SRS FR-020 says `POST .../steps/{run_step_id}/result` but the actual route is `.../steps/{stepId}/mark`. Both names appear in docs. | Confusing for API consumers; must update all SRS/data-map references. | SRS functional-specs.md:169 |
| **G4** | **`user-stories` and `acceptance-criteria` routes exist** as separate endpoints (`/api/v1/user-stories/[id]`, `/api/v1/acceptance-criteria/[id]`) but their `route.ts` handlers were not fully read — they may be GET-only or CRUD.
